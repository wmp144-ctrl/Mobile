# گزارش پایان مرحله ۱ — زیرساخت، معماری و سیستم امنیتی

تاریخ: ۳۰ مهر ۱۴۰۵ (۲۰۲۶-۱۰-۲۲)
وضعیت: **تکمیل‌شده و آزمایش‌شده** — آماده ورود به مرحله ۲ پس از تأیید کارفرما

## ۱. امکانات پیاده‌سازی‌شده

### ۱.۱ معماری و زیرساخت

- **سرور مرکزی مستقل** با NestJS و REST API روی مسیر `/api` و **کلاینت مستقل** با React/Vite؛
  در استقرار واقعی، سرور خودِ رابط کاربری ساخته‌شده را روی یک مبدأ (پورت ۳۰۰۰) سرو می‌کند تا
  کوکی نشست، CSRF و آدرس‌ها ساده و امن بمانند.
- **PostgreSQL مرکزی** با مهاجرت‌های افزایشی SQL و جدول `schema_migrations`؛ در هر راه‌اندازی فقط
  مهاجرت‌های جدید اجرا می‌شوند و به‌روزرسانی برنامه داده‌ای را حذف نمی‌کند.
- اجرای کامل **بدون اینترنت**: فونت وزیرمتن و تمام دارایی‌های رابط کاربری به‌صورت محلی بسته‌بندی
  شده‌اند؛ هیچ CDN یا سرویس بیرونی در زمان اجرا استفاده نمی‌شود.
- پشتیبانی از **چند کلاینت هم‌زمان** با استخر اتصال، تراکنش و قفل‌های پایگاه داده؛ آزمون ۵ کلاینت
  هم‌زمان با موفقیت انجام شد.
- **پشتیبان‌گیری** با `pg_dump` (دستی از رابط کاربری + خودکار روزانه ساعت ۳ بامداد)، سیاست نگهداری
  تعداد مشخص نسخه و دانلود امن نسخه پشتیبان توسط مدیر.
- **کنترل تداخل ویرایش هم‌زمان** با ستون `version` و پاسخ `409` همراه پیام راهنما.
- پیکربندی از طریق `server/.env` با اعتبارسنجی مقادیر حساس، تنظیم منطقه زمانی `Asia/Tehran` و
  امکان استقرار به‌عنوان سرویس ویندوز (مستند در `docs/DEPLOYMENT.md`).

### ۱.۲ سیستم امنیتی و ورود

- صفحه ورود فارسی و مدرن، راست‌چین و واکنش‌گرا، با نمایش نام کارگاه.
- **راه‌اندازی اولیه امن**: فقط زمانی که هیچ کاربری وجود ندارد، صفحه `/setup` فعال است؛ پس از ساخت
  مدیر کل، این مسیر برای همیشه بسته می‌شود (قفل تراکنشی در برابر ثبت هم‌زمان دو مدیر).
- رمز عبور با **bcrypt هزینه ۱۲** هش می‌شود؛ سیاست حداقل ۱۰ نویسه شامل حرف و رقم؛ رمز هرگز در
  پاسخ API یا لاگ‌ها ظاهر نمی‌شود.
- **توکن دسترسی کوتاه‌عمر (۱۵ دقیقه)** + **توکن تازه‌سازی چرخشی** ذخیره‌شده به‌صورت هش، در کوکی
  `HttpOnly` با `SameSite=Strict` و مسیر محدود `/api/auth`.
- هر بار تازه‌سازی، نشست قبلی باطل می‌شود؛ استفاده مجدد از توکن قدیمی رد می‌شود.
- **قفل خودکار پس از بی‌کاری** (پیش‌فرض ۱۰ دقیقه، قابل تنظیم ۲ تا ۲۴۰): کلاینت صفحه را قفل و توکن
  را پاک می‌کند؛ بازکردن فقط با رمز عبور و از طریق سرور انجام می‌شود. دکمه «قفل صفحه» نیز در
  منوی کاربر وجود دارد. سرور هم تازه‌سازی نشست پس از مدت بی‌کاری را رد می‌کند تا سیاست فقط به
  کلاینت وابسته نباشد.
- **قفل حساب پس از تلاش ناموفق** (پیش‌فرض ۵ تلاش / ۱۵ دقیقه) با ثبت رویداد و پیام فارسی.
- **تغییر رمز عبور** توسط کاربر (با بستن سایر نشست‌ها) و **بازنشانی رمز توسط مدیر** (با ابطال
  نشست‌های کاربر و الزام تغییر رمز در ورود بعدی).
- **مدیریت نشست‌ها**: مشاهده دستگاه‌های متصل، بستن نشست مشخص و بستن سایر نشست‌ها.
- **کنترل دسترسی نقش‌محور (RBAC)**: مجوزها در هر درخواست از پایگاه داده خوانده می‌شوند؛ غیرفعال‌شدن
  کاربر یا تغییر نقش او بلافاصله اعمال می‌شود، نه پس از انقضای توکن.
- **تاریخچه تغییرات**: ورود موفق/ناموفق، قفل حساب، خروج، تغییر رمز، بازکردن قفل، مدیریت کاربران و
  نقش‌ها، تغییر تنظیمات و پشتیبان‌گیری با کاربر، IP، مرورگر و زمان ثبت می‌شود. حذف کاربر تاریخچه را
  از بین نمی‌برد.
- محافظت CSRF با بررسی مبدأ درخواست‌های تغییردهنده + کوکی `SameSite=Strict`؛ درخواست از مبدأ
  غیرمجاز با `403` رد می‌شود.
- **حذف نرم کاربران** (نگهداری سابقه) و جلوگیری از غیرفعال‌سازی/حذف/تغییر نقش آخرین مدیر فعال و
  جلوگیری از عملیات مخرب روی حساب خود کاربر.

### ۱.۳ مدیریت کاربران، نقش‌ها و تنظیمات

- فهرست کاربران با جستجو (نام، نام کاربری، تلفن)، فیلتر نقش و وضعیت، صفحه‌بندی و نمایش آخرین ورود.
- ایجاد، ویرایش، فعال/غیرفعال‌سازی، بازنشانی رمز و حذف نرم کاربران — همراه با کنترل تداخل ویرایش.
- پنج نقش سیستمی آماده (مدیر کل، سرپرست تعمیرات، تکنسین، پذیرش، انباردار) و **ساخت نقش سفارشی**
  با انتخاب مجوزها از فهرست گروه‌بندی‌شده؛ نقش‌های سیستمی محافظت‌شده‌اند.
- تنظیمات کارگاه (نام، تلفن، آدرس) و سیاست‌های امنیتی (قفل خودکار، تلاش ناموفق، مدت قفل، اعتبار
  نشست، تعداد نسخه پشتیبان) با اعتبارسنجی و ثبت در تاریخچه.
- **داشبورد با داده واقعی**: تعداد کاربران/کاربران فعال/نشست‌ها/رویدادهای امروز، توزیع کاربران بر
  اساس نقش، آخرین رویدادها، نسخه، مدت فعالیت سرور و حجم پایگاه داده.
- رابط کاربری یکپارچه با اعلان‌های فارسی، حالت بارگذاری، حالت خالی و پیام‌های خطای سرور.

### ۱.۴ تاریخ شمسی و راست‌چین

- تمام تاریخ‌ها و ساعت‌ها با **تقویم هجری شمسی** و ارقام فارسی و منطقه زمانی تهران نمایش داده می‌شوند.
- فیلتر بازه زمانی تاریخچه با ورودی تاریخ شمسی (`۱۴۰۵/۰۷/۳۰`)، پذیرش ارقام فارسی/عربی و اعتبارسنجی.
- چیدمان کامل RTL، فونت وزیرمتن محلی و اعداد فارسی در کل رابط.

## ۳. ساختار دیتابیس مرتبط

پایگاه داده PostgreSQL ۱۸ با کدگذاری UTF-8 و این جداول:

| جدول | نقش |
| --- | --- |
| `roles` | نقش‌ها، آرایه مجوز `permissions` (jsonb)، محافظت `is_system`، نسخه |
| `users` | کاربران، هش رمز، نقش، وضعیت، قفل موقت، شمارنده تلاش، `version`، حذف نرم |
| `sessions` | نشست‌ها، هش توکن تازه‌سازی، IP/مرورگر، انقضا، ابطال |
| `audit_logs` | تاریخچه دائمی رویدادها با کاربر، شرح، جزئیات JSON، IP و زمان |
| `app_settings` | تنظیمات کلید/مقدار JSON با آخرین ویرایش‌کننده |
| `schema_migrations` | نسخه مهاجرت‌های اجراشده |

- ایندکس یکتای جزئی روی `lower(username)` برای کاربران حذف‌نشده؛ ایندکس‌های جستجو روی نقش،
  تاریخچه و نشست‌ها.
- تنظیمات پیش‌فرض: قفل خودکار ۱۰ دقیقه، ۵ تلاش ناموفق، قفل ۱۵ دقیقه، نشست ۷ روز، نگهداری ۱۴ نسخه
  پشتیبان.
- نقش‌های سیستمی و مجوزهای آینده (`customers.*`، `repairs.*`، `inventory.*`، `invoices.*`،
  `reports.*`، `files.*`) از همین حالا در پایگاه داده تعریف شده‌اند تا مراحل بعد بدون تغییر ساختار
  امنیتی اضافه شوند.

| آزمون | فرمان | نتیجه |

| بررسی نوع‌ها (سرور + کلاینت) | `npm run typecheck` | ✅ بدون خطا |
| ساخت نسخه تولید (Vite + Nest) | `npm run build` | ✅ موفق — JS ‎۴۳۸KB (gzip ۱۳۳KB)، CSS ‎۵۲KB |
| تست یکپارچگی سرور | `npm run test:server` | ✅ **۳۵ از ۳۵** |
| تست واحد و DOM کلاینت | `npm run test:client` | ✅ **۹ از ۹** |
| آزمون دود HTTP روی سرور واقعی | `node scripts/smoke-test.mjs` | ✅ **۲۱ از ۲۱** |
| سرو رابط کاربری از سرور | `curl` | ✅ `/` و `/users` با SPA fallback، دارایی‌ها `200`، خطای API فارسی |
| چند کلاینت هم‌زمان | داخل تست سرور | ✅ ۵ ورود هم‌زمان و ۱۵ درخواست موازی، همه `200` |

**پوشش تست‌های سرور (PostgreSQL ۱۸ واقعی):**

- راه‌اندازی اولیه، جلوگیری از راه‌اندازی مجدد، ذخیره نام کارگاه.
- ورود موفق/ناموفق، قفل پس از ۵ تلاش، باقی‌ماندن قفل با رمز صحیح، بازشدن پس از انقضا.
- ویژگی‌های کوکی نشست (`HttpOnly`, `SameSite=Strict`, `Path=/api/auth`).
- چرخش توکن تازه‌سازی و رد استفاده مجدد از توکن قبلی؛ باطل‌شدن توکن دسترسیِ نشست قبلی.
- بستن نشست با خروج و بی‌اعتبار شدن فوری توکن؛ مشاهده و بستن نشست‌ها.
- بازکردن قفل صفحه با رمز صحیح/غلط و بدون نشست معتبر؛ رد تازه‌سازی نشست پس از بی‌کاری طولانی
  (اعمال سیاست در سمت سرور).
- تغییر رمز و ابطال رمز قبلی؛ الزام تغییر رمز برای کاربر بازنشانی‌شده.
- دسترسی نقش‌محور: رد کاربر بدون مجوز، رد ایجاد کاربر و نقش، پنهان‌بودن مجوزها از توکن.
- کنترل تداخل `version` با پاسخ `409`؛ حفاظت آخرین مدیر و حساب خود.
- حذف نرم کاربر، حفظ تاریخچه، جلوگیری از ورود کاربر حذف‌شده.
- نقش سفارشی: ایجاد، ویرایش، کنترل نسخه و حذف؛ محافظت نقش‌های سیستمی.
- تنظیمات: پیش‌فرض‌ها، اعتبارسنجی مقادیر و ثبت تاریخچه.
- پشتیبان‌گیری: ساخت فایل، فهرست، دانلود، سیاست نگهداری و هشدار نبود ابزار.
- فیلتر و خلاصه تاریخچه، بررسی سلامت پایگاه داده، رد درخواست از مبدأ غیرمجاز.

**محدودیت‌های آزمون (صادقانه):**

1. **بازبینی بصری مرورگر** به‌صورت خودکار انجام نشده است؛ رابط کاربری در پنل Browser اجرا شده و
   بارگذاری HTML و API بررسی شده، اما تأیید نهایی ظاهر و تعامل فرم‌ها با کارفرما است.
2. ابزار `pg_dump` در محیط ابری موجود نبود؛ جریان پشتیبان‌گیری (فراخوانی، نام‌گذاری، نگهداری،
   دانلود، ثبت تاریخچه) با یک ابزار کنترل‌شده آزمایش شد. روی سرور واقعی باید PostgreSQL نصب و
   `PG_DUMP_PATH` تنظیم باشد (رابط کاربری در صورت نبود ابزار هشدار می‌دهد).
3. اجرای واقعی زمان‌بندی ساعت ۳ بامداد و بازیابی کامل با `pg_restore` آزمایش نشده است؛ دستورهای
   بازیابی مستند شده‌اند.
4. آزمون بار سنگین (بیش از ۵ کلاینت) انجام نشده است؛ معماری و استخر اتصال برای آن آماده است.

## ۶. موارد موردنیاز برای مرحله بعد

### آماده‌سازی فنی انجام‌شده

- مجوزهای `customers.view/manage`، `repairs.view/manage`، `files.manage` و `inventory.*` از قبل در
  کاتالوگ و نقش‌ها تعریف شده‌اند؛ افزودن صفحات جدید فقط نیازمند کنترل مجوز در API است.
- سرویس تاریخچه، الگوی کنترل نسخه، حذف نرم، صفحه‌بندی و فیلترهای فارسی قابل استفاده مجدد هستند.
- مهاجرت افزایشی و اسکریپت تست چندکاربره برای توسعه مرحله ۲ آماده است.

### تصمیم‌ها و اطلاعات لازم از کارفرما

1. **جزئیات دقیق نیازمندی‌های مرحله ۲** در سند ارائه‌شده ذکر نشده است (سند فعلی به بخش معماری
   مرحله ۱ ختم می‌شود). برای شروع مرحله ۲ به این موارد نیاز است:
   - فیلدهای پرونده مشتری (نام، تلفن، کد ملی؟، آدرس؟) و امکان مشتری حقیقی/حقوقی.
   - فیلدهای پذیرش دستگاه: برند، مدل، IMEI/سریال، رنگ، لوازم همراه، رمز/الگو، وضعیت ظاهری،
     توضیح خرابی، عکس‌های پیوست.
   - گردش کار تعمیر: فهرست وضعیت‌ها (مثلاً پذیرش، در انتظار بررسی، در حال تعمیر، در انتظار قطعه،
     آماده تحویل، تحویل‌شده، مرجوعی) و مجوز تغییر هر وضعیت.
   - شماره‌گذاری پرونده/رسید (مثلاً `۱۴۰۵-۰۰۰۱`) و قالب چاپ رسید پذیرش/تحویل.
   - گارانتی و شرایط مالی اولیه (هزینه تشخیص، پیش‌پرداخت، تخفیف) و اینکه فاکتور در مرحله ۳ است.
   - محل ذخیره فایل‌ها (پوشه شبکه) و مسیرهای مجاز برای عامل محلی در مرحله ۵.
2. **تأیید سیاست‌های امنیتی** فعلی (قفل ۱۰ دقیقه، ۵ تلاش، قفل ۱۵ دقیقه، نشست ۷ روز، نگهداری
   ۱۴ نسخه پشتیبان) یا اعلام مقادیر موردنظر کارگاه.
3. **آزمون پذیرش روی سرور واقعی ویندوز** توسط کارفرما: نصب PostgreSQL، تنظیم `.env`، اجرای
   `npm ci && npm run build && npm start`، ساخت مدیر، اتصال ۵ کلاینت و تأیید پشتیبان‌گیری.

### پیشنهاد اجرایی مرحله ۲ (پس از تأیید)

1. طراحی جداول `customers`، `devices`، `repair_tickets`، `repair_status_history` و پیوست‌ها با
   مهاجرت افزایشی.
2. پیاده‌سازی API و صفحات پذیرش، فهرست/جستجوی پرونده‌ها، جزئیات تعمیر و تغییر وضعیت با تاریخچه.
3. تولید شماره پرونده تراکنشی و رسید چاپی فارسی/شمسی.
4. تست یکپارچگی هم‌زمانی، مجوزها و حفظ داده مراحل قبل، سپس گزارش پایان مرحله ۲.
