نسخه سند: ۱.۰ — مرحله ۱

## ۱. نمای کلی

نرم‌افزار یک سیستم چندکاربره تحت شبکه داخلی (LAN) است. یک سرور مرکزی مسئول پایگاه داده، منطق
کسب‌وکار، احراز هویت، گزارش‌ها و فایل‌ها است و حدود ۵ کلاینت ویندوزی از طریق مرورگر به آن متصل
می‌شوند. هیچ بخشی از برنامه به اینترنت نیاز ندارد.

```
┌─────────────────────────── سرور ویندوز / لینوکس ───────────────────────────┐
│                                                                          │
│  ┌──────────────┐    ┌──────────────────────────────┐   ┌──────────────┐  │
│  │ PostgreSQL   │◄──►│  سرویس برنامه (NestJS)        │   │ پوشه فایل‌ها │  │
│  │ 18 (مرکزی)   │    │  REST API + سرو سرور UI       │   │ و پشتیبان‌ها │  │
│  └──────────────┘    └──────────────────────────────┘   └──────────────┘  │
│                                 ▲                                        │
└─────────────────────────────────┼────────────────────────────────────────┘
                                  │ HTTP/1.1 روی LAN (بدون اینترنت)
        ┌─────────────────────────┼─────────────────────────┐
        │                         │                         │
  ┌─────┴─────┐             ┌─────┴─────┐             ┌─────┴─────┐
  │ کلاینت ۱  │             │ کلاینت ۲  │             │ کلاینت ۵  │
  │ مرورگر    │             │ مرورگر    │             │ مرورگر    │
  │ + عامل محلی│            │ + عامل محلی│            │ + عامل محلی│
  └───────────┘             └───────────┘             └───────────┘
```

## ۲. تفکیک مسئولیت‌ها

| بخش | مسئولیت | فناوری |
| --- | --- | --- |
| سرور مرکزی | پایگاه داده، احراز هویت، مجوزها، منطق برنامه، گزارش‌ها، پشتیبان‌گیری، سرو فایل‌های ساخته‌شده رابط کاربری | Node.js ۲۲+، NestJS ۱۱، PostgreSQL ۱۸ |
| کلاینت | نمایش رابط کاربری فارسی/راست‌چین و ارسال درخواست‌های مجاز | React ۱۹، TypeScript، Vite، Tailwind CSS ۴ |
| عامل محلی (مرحله مربوط به فایل‌ها) | بازکردن پوشه‌های مجاز شبکه روی ویندوز، محدود به مسیرهای تعریف‌شده | Tauri (Rust) — در مرحله پنجم |
| نمودارها | نمودارهای مدیریتی | Apache ECharts — از مرحله گزارش‌ها |

**چرا PostgreSQL و نه SQLite؟** در حالت چندکلاینتی، فایل SQLite روی اشتراک شبکه باعث قفل‌شدن و
خرابی داده می‌شود. PostgreSQL روی سرور مرکزی، هم‌زمانی واقعی، تراکنش، کنترل تداخل و پشتیبان‌گیری
آنلاین را فراهم می‌کند.

**چرا SQL خام به‌جای ORM؟** لایه دسترسی داده با کوئری‌های پارامتری (`pg`) و مهاجرت‌های SQL خام
پیاده‌سازی شده است. این انتخاب کنترل کامل روی کوئری‌ها، کارایی پیش‌بینی‌پذیر، امکان استفاده از
قابلیت‌های PostgreSQL (ایندکس جزئی، `jsonb`، `FOR UPDATE`) و وابستگی کمتر برای نصب آفلاین را
می‌دهد. تمام کوئری‌ها از پارامترهای بایندشده استفاده می‌کنند و تزریق SQL ممکن نیست.

## ۴. ارتباط کلاینت و سرور

* همه درخواست‌ها روی مسیر `/api` و با REST انجام می‌شوند.
* در استقرار واقعی، سرویس سرور خودِ رابط کاربری ساخته‌شده را نیز سرو می‌کند؛ بنابراین کلاینت‌ها
  فقط به `http://SERVER-IP:3000` وصل می‌شوند و مسئله CORS وجود ندارد.
* در حالت توسعه، Vite روی پورت ۳۰۰۰ و سرور روی ۳۰۰۱ اجرا می‌شود و `/api` پروکسی می‌شود.
* قالب خطاها یکسان است: `{ statusCode, code, message, details, path, timestamp }` و پیام‌ها فارسی.

## ۵. مدل امنیتی (مرحله ۱)

| موضوع | تصمیم |
| --- | --- |
| رمز عبور | هش bcrypt با هزینه ۱۲؛ حداقل ۱۰ نویسه شامل حرف و رقم؛ هرگز بازگردانده نمی‌شود |
| توکن دسترسی | JWT کوتاه‌عمر (۱۵ دقیقه) فقط با شناسه کاربر و شناسه نشست |
| نشست | توکن تازه‌سازی تصادفی ۴۸ بایتی، هش‌شده در پایگاه داده، کوکی `HttpOnly` با `SameSite=Strict` |
| چرخش توکن | هر بار تازه‌سازی، نشست قبلی باطل و نشست جدید صادر می‌شود؛ استفاده مجدد از توکن باطل‌شده رد می‌شود |
| مجوزها | نقش‌ها دارای آرایه مجوز (`*` برای مدیر کل)؛ بررسی مجوز در هر درخواست از پایگاه داده (نه از توکن) تا لغو دسترسی فوری اعمال شود |
| قفل خودکار | عدم فعالیت بیش از مدت تنظیم‌شده ⇒ قفل صفحه؛ بازکردن فقط با رمز عبور و از طریق سرور انجام می‌شود. سرور نیز تازه‌سازی نشست پس از مدت بی‌کاری را رد می‌کند |
| تلاش ناموفق | پس از ۵ تلاش، حساب به‌مدت ۱۵ دقیقه قفل می‌شود (قابل تنظیم) و رویداد ثبت می‌شود |
| تاریخچه | تمام رویدادهای ورود/خروج/تغییر رمز/مدیریت کاربران و تنظیمات در `audit_logs` ثبت می‌شود |
| CSRF | کوکی تازه‌سازی فقط به مسیر `/api/auth` ارسال می‌شود، `SameSite=Strict` است و درخواست‌های تغییردهنده با مبدأ غیرمجاز رد می‌شوند |
| رمز اولیه مدیر | فقط در اولین راه‌اندازی و تنها وقتی هیچ کاربری وجود ندارد؛ پس از آن endpoint بسته می‌شود |

## ۶. جلوگیری از تداخل ویرایش هم‌زمان

هر رکورد کاربر و نقش دارای ستون `version` است. هنگام ویرایش، نسخه خوانده‌شده همراه درخواست ارسال
می‌شود؛ اگر نسخه پایگاه داده متفاوت باشد پاسخ `409` با پیام «اطلاعات توسط کاربر دیگری تغییر کرده
است» برگردانده می‌شود و کاربر می‌تواند داده تازه را ببیند. این الگوی خوش‌بینانه در مراحل بعد برای
پرونده‌های تعمیر و انبار نیز استفاده می‌شود.

## ۷. پشتیبان‌گیری

* پشتیبان منطقی با `pg_dump` در قالب custom و در پوشه `BACKUP_DIR` ذخیره می‌شود.
* پشتیبان روزانه خودکار (ساعت ۳ بامداد) با نگهداری N نسخه آخر و امکان پشتیبان‌گیری دستی توسط مدیر.
* دانلود فایل پشتیبان از داخل برنامه، فقط برای کاربر دارای مجوز `backups.manage`.
* بازیابی به‌صورت مستندشده با `pg_restore` انجام می‌شود تا عملیات مخرب از رابط کاربری حذف شود.
