# معماری نرم‌افزار مدیریت تعمیرگاه موبایل و تجهیزات الکترونیکی

نسخه سند: ۱.۳ — مراحل ۱ تا ۵
وضعیت: مراحل ۱ تا ۶ پیاده‌سازی و آزمایش شده‌اند

---

## ۱. نمای کلی

نرم‌افزار یک سیستم چندکاربره تحت شبکه داخلی (LAN) است. یک سرور مرکزی مسئول پایگاه داده، منطق
کسب‌وکار، احراز هویت، گزارش‌ها و فایل‌ها است و حدود ۵ کلاینت ویندوزی از طریق مرورگر به آن متصل
می‌شوند. هیچ بخشی از برنامه به اینترنت نیاز ندارد.

```
┌─────────────────────────── سرور ویندوز / لینوکس ───────────────────────────┐
│                                                                          │
│  ┌──────────────┐    ┌──────────────────────────────┐   ┌──────────────┐  │
│  │ PostgreSQL   │◄──►│  سرویس برنامه (NestJS)        │   │ پوشه فایل‌ها │  │
│  │ 18 (مرکزی)   │    │  REST API + سرو سرور UI       │   │ و پشتیبان‌ها │  │
│  └──────────────┘    └──────────────────────────────┘   └──────────────┘  │
│                                 ▲                                        │
└─────────────────────────────────┼────────────────────────────────────────┘
                                  │ HTTP/1.1 روی LAN (بدون اینترنت)
        ┌─────────────────────────┼─────────────────────────┐
        │                         │                         │
  ┌─────┴─────┐             ┌─────┴─────┐             ┌─────┴─────┐
  │ کلاینت ۱  │             │ کلاینت ۲  │             │ کلاینت ۵  │
  │ مرورگر    │             │ مرورگر    │             │ مرورگر    │

  └───────────┘             └───────────┘             └───────────┘
```

## ۲. تفکیک مسئولیت‌ها

| بخش | مسئولیت | فناوری |
| --- | --- | --- |
| سرور مرکزی | پایگاه داده، احراز هویت، مجوزها، منطق برنامه، گزارش‌ها، پشتیبان‌گیری، سرو فایل‌های ساخته‌شده رابط کاربری | Node.js ۲۲+، NestJS ۱۱، PostgreSQL ۱۸ |
| کلاینت | نمایش رابط کاربری فارسی/راست‌چین و ارسال درخواست‌های مجاز | React ۱۹، TypeScript، Vite، Tailwind CSS ۴ |
| برنامه کمکی کلاینت | بازکردن پوشه‌های مجاز شبکه روی ویندوز با بلیت یک‌بارمصرف | PowerShell + پروتکل `repairdesk://` — مرحله ۳ |
| نمودارها | نمودارهای مدیریتی | Apache ECharts ۶ — از مرحله ۴ |

**چرا PostgreSQL و نه SQLite؟** در حالت چندکلاینتی، فایل SQLite روی اشتراک شبکه باعث قفل‌شدن و
خرابی داده می‌شود. PostgreSQL روی سرور مرکزی، هم‌زمانی واقعی، تراکنش، کنترل تداخل و پشتیبان‌گیری
آنلاین را فراهم می‌کند.

**چرا SQL خام به‌جای ORM؟** لایه دسترسی داده با کوئری‌های پارامتری (`pg`) و مهاجرت‌های SQL خام
پیاده‌سازی شده است. این انتخاب کنترل کامل روی کوئری‌ها، کارایی پیش‌بینی‌پذیر، امکان استفاده از
قابلیت‌های PostgreSQL (ایندکس جزئی، `jsonb`، `FOR UPDATE`) و وابستگی کمتر برای نصب آفلاین را
می‌دهد. تمام کوئری‌ها از پارامترهای بایندشده استفاده می‌کنند و تزریق SQL ممکن نیست.

## ۴. ارتباط کلاینت و سرور

* همه درخواست‌ها روی مسیر `/api` و با REST انجام می‌شوند.
* در استقرار واقعی، سرویس سرور خودِ رابط کاربری ساخته‌شده را نیز سرو می‌کند؛ بنابراین کلاینت‌ها
  فقط به `http://SERVER-IP:3000` وصل می‌شوند و مسئله CORS وجود ندارد.
* در حالت توسعه، Vite روی پورت ۳۰۰۰ و سرور روی ۳۰۰۱ اجرا می‌شود و `/api` پروکسی می‌شود.
* قالب خطاها یکسان است: `{ statusCode, code, message, details, path, timestamp }` و پیام‌ها فارسی.

## ۵. مدل امنیتی (مرحله ۱)

| موضوع | تصمیم |
| --- | --- |
| رمز عبور | هش bcrypt با هزینه ۱۲؛ حداقل ۱۰ نویسه شامل حرف و رقم؛ هرگز بازگردانده نمی‌شود |
| توکن دسترسی | JWT کوتاه‌عمر (۱۵ دقیقه) فقط با شناسه کاربر و شناسه نشست |
| نشست | توکن تازه‌سازی تصادفی ۴۸ بایتی، هش‌شده در پایگاه داده، کوکی `HttpOnly` با `SameSite=Strict` |
| چرخش توکن | هر بار تازه‌سازی، نشست قبلی باطل و نشست جدید صادر می‌شود؛ استفاده مجدد از توکن باطل‌شده رد می‌شود |
| مجوزها | نقش‌ها دارای آرایه مجوز (`*` برای مدیر کل)؛ بررسی مجوز در هر درخواست از پایگاه داده (نه از توکن) تا لغو دسترسی فوری اعمال شود |
| قفل خودکار | عدم فعالیت بیش از مدت تنظیم‌شده ⇒ قفل صفحه؛ بازکردن فقط با رمز عبور و از طریق سرور انجام می‌شود. سرور نیز تازه‌سازی نشست پس از مدت بی‌کاری را رد می‌کند |
| تلاش ناموفق | پس از ۵ تلاش، حساب به‌مدت ۱۵ دقیقه قفل می‌شود (قابل تنظیم) و رویداد ثبت می‌شود |
| تاریخچه | تمام رویدادهای ورود/خروج/تغییر رمز/مدیریت کاربران و تنظیمات در `audit_logs` ثبت می‌شود |
| CSRF | کوکی تازه‌سازی فقط به مسیر `/api/auth` ارسال می‌شود، `SameSite=Strict` است و درخواست‌های تغییردهنده با مبدأ غیرمجاز رد می‌شوند |
| رمز دستگاه | رمز/الگوی دستگاه مشتری با AES-256-GCM و IV تصادفی رمز می‌شود؛ نمایش فقط با مجوز `repairs.manage` و ثبت در تاریخچه |
| پیوست‌ها | تصاویر دستگاه خارج از پوشه عمومی و از مسیری احراز هویت‌شده سرو می‌شوند |
| رمز اولیه مدیر | فقط در اولین راه‌اندازی و تنها وقتی هیچ کاربری وجود ندارد؛ پس از آن endpoint بسته می‌شود |

## ۶. جلوگیری از تداخل ویرایش هم‌زمان

هر رکورد کاربر و نقش دارای ستون `version` است. هنگام ویرایش، نسخه خوانده‌شده همراه درخواست ارسال
می‌شود؛ اگر نسخه پایگاه داده متفاوت باشد پاسخ `409` با پیام «اطلاعات توسط کاربر دیگری تغییر کرده
است» برگردانده می‌شود و کاربر می‌تواند داده تازه را ببیند. این الگوی خوش‌بینانه اکنون در پرونده‌های
تعمیر (دستگاه و اقدامات) نیز پیاده شده و در مراحل بعد برای انبار استفاده می‌شود.

## ۷. پشتیبان‌گیری و بازیابی

* هر پشتیبان یک بسته مستقل (`backup-YYYYMMDD-HHMMSS/`) شامل `manifest.json`، `database.dump`،
  `settings.json` و در صورت انتخاب `uploads` است.
* رمزنگاری اختیاری با AES-256-GCM روی هر فایل؛ کلید با scrypt از `BACKUP_PASSPHRASE` مشتق
  می‌شود و ذخیره نمی‌گردد. مانیفست شامل SHA-256، IV و Tag هر فایل است.
* زمان‌بندی روزانه از تنظیمات (`backup.scheduleTime` و منطقه زمانی) خوانده می‌شود؛ هر روز حداکثر یک
  اجرای خودکار و با جبران حداکثر ۹۰ دقیقه‌ای انجام می‌شود. `BACKUP_CRON_ENABLED=false` کل زمان‌بندی
  را در سطح سرور خاموش می‌کند.
* بازیابی از رابط کاربری با تأیید نام بسته، انتخاب بخش‌ها و ساخت نسخه ایمن `pre_restore` انجام
  می‌شود. `pg_restore` با `--clean --if-exists --no-owner --single-transaction` اجرا می‌گردد.
* بازیابی تنظیمات به‌صورت upsert روی `app_settings`، `field_definitions` و `option_lists` است و
  کاربران/نشست‌ها را تغییر نمی‌دهد.
* نتیجه هر عملیات در `backup_runs` ثبت می‌شود؛ آخرین موفقیت و آخرین شکست مبنای هشدار رابط کاربری‌اند.
* همه عملیات با مجوز `backups.manage` انجام و در `audit_logs` ثبت می‌شود.
* جزئیات عملیاتی: [BACKUP-RESTORE.md](BACKUP-RESTORE.md).

## ۸. ذخیره‌سازی فایل و شبکه

* مسیر ذخیره‌سازی در رکورد `storage_locations` با دو نمایش نگهداری می‌شود: مسیر سرور برای ساخت،
  بررسی و محاسبه حجم، و مسیر کلاینتی/UNC برای بازکردن روی رایانه کاربر.
* هنگام پذیرش، سرویس مرکزی پوشه `سال شمسی/کد پذیرش` و زیرپوشه‌های پیکربندی‌شده را می‌سازد. خطای
  ساخت پوشه، پذیرش را متوقف نمی‌کند و مسیر با وضعیت هشدار ثبت می‌شود.
* سلامت حافظه (ظرفیت، فضای آزاد، نوشتن و آخرین دسترسی موفق) با محدودیت زمانی بررسی می‌شود تا
  قطع بودن هارد یا کندی NAS، صفحه را قفل نکند.
* بازکردن پوشه با بلیت تصادفی یک‌بارمصرف انجام می‌شود. برنامه وب هرگز مسیر دلخواه را به سیستم‌عامل
  نمی‌فرستد؛ فقط برنامه کمکی، مسیر تأییدشده سرور را با Explorer باز می‌کند.
* نمایش مسیرهای بکاپ با مجوز `files.view` و تغییر آن‌ها با `files.manage` کنترل می‌شود.

## ۹. داشبورد و گزارش‌گیری تحلیلی

* تمام آمار در سرور و با SQL تجمعی محاسبه می‌شود؛ کلاینت فقط نتیجه گروه‌بندی‌شده را دریافت می‌کند
  و ردیف‌های خام دستگاه‌ها به مرورگر منتقل نمی‌شوند.
* گروه‌بندی ماهانه و سالانه با توابع `ir_jalali_year`، `ir_jalali_month` و `ir_jalali_ym` در
  PostgreSQL و بر پایه منطقه زمانی `Asia/Tehran` انجام می‌شود تا نتیجه به ساعت کلاینت وابسته نباشد.
* یک مجموعه فیلتر (`AnalyticsFilter`) روی کارت‌های آماری، همه نمودارهای داشبورد و گزارش‌های
  پیشرفته اعمال می‌شود؛ گزارش‌های چندنموداری همان فیلترها را برای همه نمودارها به کار می‌برند.
* قالب گزارش شامل فیلترها، فهرست و ترتیب نمودارها، شاخص، فیلد گروه‌بندی و ستون‌های جدول است و
  در جدول `saved_reports` به‌صورت JSONB با شماره نسخه ذخیره می‌شود.
* خروجی‌های Excel و CSV در سرور تولید می‌شوند؛ PDF و PNG در مرورگر از ECharts و DOM ساخته
  می‌شوند و لوگوی کارگاه از تنظیمات خوانده می‌شود.
* دسترسی به داشبورد با `dashboard.view`، اجرای گزارش با `reports.view` و ساخت/ویرایش قالب با
  `reports.manage` کنترل می‌شود.

## ۱۰. تنظیمات، توسعه‌پذیری و ظاهر

* تنظیمات در جدول کلید/مقدار `app_settings` با JSONB ذخیره می‌شوند و سرویس `SettingsService`
  مقادیر پیش‌فرض امن را برای کلیدهای غایب برمی‌گرداند. بنابراین نبود یک کلید باعث خطا نمی‌شود.
* تنظیمات ظاهر و تاریخ/ساعت (`app.theme`، `app.accentColor`، `app.language`، `app.calendar`،
  `app.timezone`، `app.timeFormat`) در `GET /api/public/info` هم منتشر می‌شوند تا صفحه ورود و
  همه کاربران، مستقل از مجوز `settings.view`، همان پوسته را ببینند.
* کلاینت تنظیمات را در `useAppearance` نگه می‌دارد و با `data-theme`، `data-accent`، `lang` و
  `dir` روی `<html>` اعمال می‌کند؛ قالب‌بندی تاریخ و ارقام نیز از همین منبع تغذیه می‌شود.
* فیلدهای فرم در `field_definitions` تعریف می‌شوند. پرچم‌های `is_searchable` و `is_reportable`
  تعیین می‌کنند مقدار فیلد در جست‌وجوی سراسری و ستون‌های گزارش استفاده شود یا نه. جست‌وجو با
  `jsonb_each_text` و اتصال به تعریف فیلد انجام می‌شود و ستون گزارش با کلید `custom:<field_key>`
  به SQL امن (کلید از پایگاه داده، نه ورودی کاربر) تبدیل می‌گردد.
* غیرفعال‌سازی فیلد فقط نمایش و اعتبارسنجی جدید را تغییر می‌دهد؛ داده در `devices.custom_fields`
  باقی می‌ماند. حذف فیزیکی فیلدهای سیستمی ممنوع است.
* وضعیت دستگاه در `devices.status` ذخیره می‌شود و برچسب/ترتیب آن در `option_lists` با دسته
  `device_status` نگهداری می‌شود. وضعیت‌های پیش‌فرض، معنی‌های تحلیلی (`active`/`closed`/`tone`) را در
  کد دارند؛ وضعیت سفارشی مدیر «کار در جریان» با رنگ اطلاعاتی است. اعتبارسنجی وضعیت در سرویس
  انجام می‌شود، بنابراین افزودن وضعیت جدید به انتشار مجدد کد نیاز ندارد.
