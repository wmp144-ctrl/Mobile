# راهنمای مدیریت و نگهداری سرور

این سند برای مدیر سرور نوشته شده است: اجرا، پایش، به‌روزرسانی، امنیت، ظرفیت و رفع اشکال.

## ۱. معماری اجرا

```
مرورگر کلاینت‌ها ──HTTP──> Node.js/NestJS (پورت ۳۰۰۰) ──> PostgreSQL (فقط localhost)
                                   │
                                   ├── رابط ساخته‌شده در client/dist
                                   ├── uploads (تصاویر دستگاه‌ها)
                                   ├── storage (پوشه‌های Original/Backup)
                                   └── backups (بسته‌های پشتیبان)
```

* هیچ سرویس ابری یا اینترنت لازم نیست؛ فونت‌ها و دارایی‌های رابط کاربری محلی هستند.
* کلاینت‌ها فقط به پورت ۳۰۰۰ نیاز دارند؛ پورت ۵۴۳۲ نباید از شبکه باز باشد.
* سرویس را با `NSSM` یا Task Scheduler به‌صورت خودکار اجرا کنید (نمونه در DEPLOYMENT.md).

## ۲. پایش روزانه

| مورد | روش |
| --- | --- |
| سلامت سرویس | `GET /api/health` (وضعیت `ok` و `database: up`) |
| خطاهای اجرا | `logs/service-err.log` (تنظیم `AppStderr` در NSSM) |
| آخرین پشتیبان موفق | تنظیمات ← پشتیبان‌گیری و بازیابی (نشان سبز و تاریخ) |
| شکست پشتیبان | هشدار قرمز در همان صفحه + ردیف «ناموفق» در تاریخچه عملیات |
| فضای دیسک | فضای `BACKUP_DIR`، `UPLOADS_DIR`، `STORAGE_ROOT` و دیسک پایگاه داده |
| نشست‌های فعال | داشبورد عملیاتی یا `GET /api/auth/sessions` |
| تاریخچه حساس | «تاریخچه» با فیلتر ورود ناموفق، تغییر تنظیمات و پشتیبان‌گیری |

فرمان‌های نمونه ویندوز:

```powershell
Invoke-RestMethod http://127.0.0.1:3000/api/health
Get-Content C:\RepairWorkshop\logs\service-err.log -Tail 100
Get-PSDrive D | Select-Object Used,Free
```

## ۳. پایگاه داده

```powershell
# اندازه پایگاه داده
psql -U repair_app -d repair_workshop -c "SELECT pg_size_pretty(pg_database_size('repair_workshop'));"

# اتصال‌های فعال
psql -U repair_app -d repair_workshop -c "SELECT count(*), state FROM pg_stat_activity GROUP BY state;"

# وضعیت مهاجرت‌ها
psql -U repair_app -d repair_workshop -c "SELECT name, applied_at FROM schema_migrations ORDER BY name;"
```

* مهاجرت‌ها در `server/src/database/migrations` به‌صورت افزایشی اجرا می‌شوند و در
  `schema_migrations` ثبت می‌گردند. هرگز فایل مهاجرت اجراشده را تغییر ندهید؛ برای تغییر جدید، فایل
  شماره بعدی را اضافه کنید.
* `DB_AUTO_MIGRATE=true` مهاجرت‌ها را هنگام شروع سرویس اجرا می‌کند. برای به‌روزرسانی کنترل‌شده
  می‌توانید موقتاً `false` کنید، پشتیبان بگیرید و سپس سرویس را با `true` بالا بیاورید.
* `DB_POOL_MAX` پیش‌فرض ۱۰ است؛ برای پنج کلاینت کافی است. از افزایش بی‌دلیل آن خودداری کنید.
* نمایه‌های مهم: `devices` (کد پذیرش، وضعیت، IMEI/سریال)، `audit_logs (created_at)`،
  `saved_reports`، `backup_runs (created_at)` و `field_definitions` (قابل جست‌وجو).

## ۴. فضای دیسک و نگهداری داده

| پوشه | محتوا | سیاست پیشنهادی |
| --- | --- | --- |
| `uploads` | تصاویر دستگاه‌ها | بخشی از بسته پشتیبان در صورت فعال بودن |
| `storage` | پوشه‌های Original/Backup دستگاه‌ها | کپی روزانه با Robocopy/NAS |
| `backups` | بسته‌های پشتیبان | N نسخه آخر + کپی ماهانه روی دیسک دوم |

* هشدار فضای آزاد در صفحه «فایل و بکاپ» با آستانه `storage.lowSpaceGb` (پیش‌فرض ۵ گیگابایت) نشان
  داده می‌شود.
* `audit_logs` رشد می‌کند؛ برای نگهداری طولانی، دوره‌ای آن را آرشیو کنید (مثلاً رویدادهای قدیمی‌تر از
  دو سال را در جدول آرشیو منتقل کنید) و هرگز بدون پشتیبان حذف نکنید.

## ۵. به‌روزرسانی بدون حذف اطلاعات

1. از پایگاه داده و تنظیمات پشتیبان بگیرید (`/api/backups` یا دکمه تنظیمات).
2. سرویس را متوقف کنید: `nssm stop RepairWorkshop`.
3. از پوشه فعلی یک کپی داشته باشید (به‌جز `node_modules` و `backups`).
4. فایل‌های نسخه جدید را جایگزین کنید؛ `server/.env` و پوشه‌های داده را نگه دارید.
5. `npm ci` و `npm run build` را اجرا کنید.
6. سرویس را شروع کنید. مهاجرت‌های جدید افزایشی اجرا می‌شوند و داده موجود حفظ می‌شود.
7. `GET /api/health`، ورود مدیر و یک گزارش/پرونده را بررسی کنید.

نکته: اگر مهاجرتی شکست خورد، سرویس بالا نمی‌آید. لاگ را بخوانید، سرویس را متوقف و نسخه پشتیبان
پیش از به‌روزرسانی را بازیابی کنید.

## ۶. امنیت بهره‌برداری

* `JWT_SECRET` و `DEVICE_SECRET` را تصادفی و حداقل ۳۲ نویسه نگه دارید؛ تغییر `DEVICE_SECRET` باعث
  غیرقابل‌خواندن شدن رمزهای ذخیره‌شده دستگاه می‌شود.
* `BACKUP_PASSPHRASE` را در گاوصندوق یا مدیر رمز سازمانی نگه دارید؛ در فایل عمومی یا ایمیل نگذارید.
* فایل `server/.env` را فقط برای کاربر سرویس قابل خواندن کنید:
  `icacls "C:\RepairWorkshop\server\.env" /inheritance:r /grant:r "SYSTEM:(R)" "Administrators:(R)"`.
* `COOKIE_SECURE=false` فقط برای HTTP در شبکه داخلی است؛ در صورت استفاده از HTTPS آن را `true` کنید.
* پورت ۵۴۳۲ را از شبکه ببندید و رمز `repair_app` را دوره‌ای تغییر دهید.
* کاربر سرویس ویندوز باید حداقل دسترسی لازم به `uploads`, `storage`, `backups` را داشته باشد
  (نه Administrator).
* نسخه‌های پشتیبان و پوشه فایل‌ها را از دسترس اشتراک عمومی خارج کنید.
* حساب‌های غیرفعال را غیرفعال کنید و رمزهای پیش‌فرض را در اولین ورود تغییر دهید.

## ۷. آزمون اتصال چند کلاینت

سرور بدون حالت است و هر کلاینت نشست مستقل دارد. برای آزمون بار سبک:

1. پنج مرورگر/پروفایل مختلف (یا پنج دستگاه) را به سرور وصل کنید.
2. هم‌زمان یک دستگاه را در دو کلاینت باز کنید؛ یکی را ویرایش و ذخیره کنید، دیگری را با نسخه قدیمی
   ذخیره کنید؛ باید پاسخ «اطلاعات توسط کاربر دیگری تغییر کرده است» بگیرید.
3. در یک کلاینت وضعیت دستگاه را تغییر دهید و در کلاینت دیگر تاریخچه را تازه کنید.
4. گزارش سنگین (بازه یک‌ساله با هفت نمودار) را هم‌زمان در دو کلاینت اجرا کنید و زمان پاسخ و
   مصرف CPU/RAM سرور را ببینید.
5. اتصال شبکه یکی از کلاینت‌ها را قطع و وصل کنید؛ نشست باید با تازه‌سازی کوکی ادامه یابد.

## ۸. کارهای دوره‌ای

| دوره | کار |
| --- | --- |
| روزانه | بررسی سلامت، فضای دیسک، آخرین پشتیبان و لاگ خطا |
| هفتگی | بررسی تاریخچه ورود ناموفق و رویدادهای حساس، کپی فایل‌ها |
| ماهانه | کپی پشتیبان روی دیسک جداگانه، بررسی اندازه پایگاه داده، به‌روزرسانی امنیتی سیستم‌عامل |
| هر سه ماه | آزمون بازیابی واقعی روی پایگاه داده آزمایشی (BACKUP-RESTORE.md) |
| سالانه | بازبینی نقش‌ها و مجوزها، چرخش رمزها و بازبینی سیاست نگهداری داده |

## ۹. رفع اشکال سریع

| نشانه | اقدام |
| --- | --- |
| سرویس بالا نمی‌آید | `logs/service-err.log`؛ اعتبار `DATABASE_URL`؛ خطای مهاجرت |
| ۵۰۲/عدم دسترسی | سرویس و پورت ۳۰۰۰؛ فایروال |
| «ارتباط با سرور برقرار نشد» | شبکه داخلی، IP سرور، سلامت `/api/health` |
| پشتیبان خطا می‌دهد | `PG_DUMP_PATH`، دسترسی نوشتن، فضای دیسک، `BACKUP_PASSPHRASE` |
| بازیابی خطا می‌دهد | `PG_RESTORE_PATH`، خارج بودن کاربران، فضای دیسک |
| تصویر نمایش داده نمی‌شود | `UPLOADS_DIR` و دسترسی خواندن |
| وضعیت حافظه «قطع» | هارد/NAS، دسترسی کاربر سرویس، مسیر سرور |
| کندی گزارش | بازه را محدود کنید، `DB_POOL_MAX` و منابع سرور را بررسی کنید |
| زمان‌ها اشتباه است | `TZ=Asia/Tehran`، ساعت ویندوز و منطقه زمانی تنظیمات |

## ۱۰. توقف و انتقال سرور

* برای انتقال، ابتدا پشتیبان کامل بگیرید (پایگاه داده + تنظیمات + فایل‌ها).
* روی سرور جدید PostgreSQL و Node را نصب، `.env` را با مقادیر جدید تنظیم و مهاجرت‌ها را اجرا کنید.
* پوشه‌های `uploads`, `storage`, `backups` را منتقل و دسترسی کاربر سرویس را تنظیم کنید.
* پس از بازیابی، ورود مدیر، تعداد تجهیزات، یک گزارش و یک پشتیبان‌گیری را بررسی کنید و سپس IP/آدرس
  کلاینت‌ها را به‌روزرسانی کنید.
